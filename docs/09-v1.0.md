# v1.0: new log sources, a response layer, and a blind test

*Author: [github.com/amarkralj](https://github.com/amarkralj)*

v1.0 extends NullProtocol Negative Trust, an extension of zero trust for insider threats, in two directions:

1. **More systems.** GitHub, Google Workspace and Google Cloud, Kubernetes, AWS data-movement services, AI assistants
   (Amazon Bedrock, Microsoft 365 Copilot) and AI agents (coding CLIs, MCP servers, local model servers).
2. **The response chain.** A containment decision now becomes concrete, documented API calls in the systems a company
   already runs (Microsoft Entra ID, Okta, Google Workspace, AWS IAM, GitHub, Kubernetes, any OpenID Shared Signals
   receiver), with approval gates, undo, and a hash-chained record of every action.

## Headline: the blind test

The new rules were written while looking at 55 recorded attack datasets. A score on those datasets says little about
data the rules have not seen. So, before testing, we picked every further dataset in
[splunk/attack_data](https://github.com/splunk/attack_data) from the same families that no earlier release had
downloaded (30 datasets, 23 scored), wrote down from their names alone what should be detected, committed the rules,
and only then downloaded the files and ran the frozen rules once.

| | Development set (rules written on it) | Hold-out (blind, rules frozen) |
|---|---|---|
| v0.9 rules | 11 / 45 | 5 / 23 |
| **v1.0 rules** | **44 / 45** (first run: 43) | **5 / 23** |
| no event could be read | 1 (file truncated at the source) | 14 |
| read, but missed | 0 | 4 |

**On unseen data, v1.0 added nothing over v0.9.** Every hold-out detection came from older rules. The 44 / 45 mostly
measures fit to the development data.

Why the hold-out failed (analysed after the run; the recorded result stays as it is):

* **Allow-lists of operation names do not generalise.** The adapters map each audit operation explicitly and drop the
  rest. Nine AWS datasets were missed only because their operations were not on a list: `DeleteGuardrail`,
  `DeleteKnowledgeBase`, `PutBucketVersioning`, `CreateVirtualMFADevice`, `DeactivateMFADevice`,
  `DeleteVirtualMFADevice`, `AuthorizeSecurityGroupIngress`, `DeleteModelInvocationLoggingConfiguration`,
  password-policy changes.
* **Formats without an adapter:** Azure Activity logs (2), Entra "User Risk Detection" audit records (1), Windows XML
  event logs (2). The last two were also our pre-registration mistake: `gdrive` and `generic_password_spray` turned out
  to be endpoint logs, not cloud audit logs.
* **Read but missed (4):** AzureHound reconnaissance (raised as bulk data access, not discovery); password-policy
  discovery (no rule); console sign-ins from several networks (the concurrent-network rule needs two different clients);
  disabling the consent block for risky apps (raised as an identity change, not as audit tampering).

The lesson for v1.1 is structural: classify cloud operations by verb and object (delete / disable / deactivate on a
security object, create / attach on an identity object) instead of by name, and read Azure Activity logs. Those changes
need a new blind test on data not yet seen; re-scoring this hold-out after changing the rules would not be blind.

## Development results in detail

`results/v10_first_run.json` (first run, never overwritten), `results/v10.json` (latest).

| Family | Datasets scored | v0.9 | v1.0 |
|---|---|---|---|
| Session hijacking, spraying, device-code phishing (Entra, Microsoft 365, AWS, Okta) | 6 | 1 | 6 |
| GitHub supply chain (protections removed, audit streaming, destructive changes, runners) | 12 | 3 | 11 (1 file truncated at the source) |
| Google Workspace and Google Cloud | 9 | 6 | 9 |
| Kubernetes audit | 8 | 0 | 8 |
| AWS data movement | 2 | 1 | 2 |
| AI assistants and agents (Bedrock, Copilot, Gemini CLI) | 8 | 0 | 8 (first run: 7) |

Bugs found on the development set and fixed before the freeze, each recorded in git:

* The Gemini CLI pattern needed two spaces before `--yolo` (first run: missed).
* The new concurrent-network rule raised evidence on 14 earlier datasets where it was not expected. It now counts only
  sign-ins and read calls, from two networks of the same IP family, used by two different clients within 10 minutes.
  AWS writes the placeholder "AWS Internal" as the client of console calls; it names no device and counts as unknown.

Precision where the data contains both ordinary use and attacks:

| Dataset | Flagged | Comment |
|---|---|---|
| Bedrock prompt injection (15 attack prompts) | 15 / 15 | |
| Bedrock hostile tone (15 rude but not injecting prompts) | 0 / 15 | correct: insults are not injections |
| Microsoft 365 Copilot export (19 ordinary prompts, 6 jailbreaks) | 3 of 6 jailbreaks, 0 of 19 ordinary | the export truncates titles at about 50 characters |
| Bedrock "sensitive data in prompts" (13) | 5 / 13 | the 5 contain credential values; the other 8 only name secrets or show error messages |
| Bedrock excessive tokens (40 requests, 4 users) | exactly the 4 large responses | each answers a request to dump salaries, customer records or secrets |

Pattern detectors for prompts catch the published, copy-pasted forms and are easy to evade by rewording. They are
evidence for the trust model, not a filter that makes a model safe.

## Regression

* **118 earlier recorded datasets** (Splunk cloud and Okta, `results/v10_regression.json`): no detection lost, 4 gained
  (two distributed-spraying and two concurrent-session datasets that v0.9 missed). v1.0 raises new evidence on 7
  datasets where it was not expected (concurrent networks; weight 1.0, which means a step-up sign-in for the account,
  not a restriction). Lab captures often mix several test runs from different networks, so some of these may be real;
  we count them as possible false alarms.
* **Simulator** (240 runs, `results/v10_sim.json`): prevention, containment, wrongly blamed victims and innocent
  step-ups are identical to v0.9. The simulator does not generate GitHub, Kubernetes or AI events, so this shows that
  v1.0 does no harm there, not that it helps.
* **CERT:** the v1.0 rules need IP addresses, cloud audit or AI logs, which CERT does not contain; not re-run.

## The response layer (`npcore.respond`, `npcore respond`)

| Level or evidence | Action | Runs |
|---|---|---|
| L1 / L2 | Signed CAEP `risk-level-change` to any Shared Signals receiver (JWS HS256) | automatically |
| L3 | Revoke sign-in sessions: Entra `revokeSignInSessions`, Okta `DELETE /users/{id}/sessions`, Google `signOut`, AWS deny-older-sessions role policy (`aws:TokenIssueTime`) | automatically |
| L4 | Suspend the account in Entra, Okta, Google | only after a person approves |
| Stolen session or device-code phishing (account evidence) | Revoke sessions (the victim signs in again) | automatically |
| Branch protection removed | Restore it (GitHub REST) | automatically |
| Privileged pod created | Delete the pod (Kubernetes API) | only after approval |
| AI coding CLI started with all approvals off | Stop the process | only after approval |

* Dry run is the default: `npcore respond <log files> --systems ssf,entra,okta` prints the plan with the documented
  endpoint of each action. `--execute` runs actions whose connector token is set (`NP_ENTRA_TOKEN`, `NP_OKTA_TOKEN`,
  `NP_GOOGLE_TOKEN`, `NP_GITHUB_TOKEN`, `NP_K8S_TOKEN`, `NP_SSF_TOKEN`); actions that need approval run only with
  `--approve <id>`. AWS and host actions are printed as CLI commands, never run by the tool.
* Every planned, started and finished action is written to a hash-chained ledger *before* it runs
  (`npcore verify-ledger`). Every action carries its undo.
* `tests/test_v10.py` runs the chain against a live local HTTP receiver: the receiver checks the event signature, and
  an action that needs approval does not arrive until it is approved.
* **Not yet tested against real tenants.** The request shapes follow the vendors' documentation (linked in the code);
  they have not been executed against a real Entra, Okta, Google, AWS or GitHub organisation.

## How to check every number

`results/v10_proof.json` lists the commit that fixed each pre-registration, the commit that froze the rules before the
hold-out download, the SHA-256 of the rule files at that commit, of every input file (95) and of every result file,
and the commands to reproduce. Re-running the hold-out at the freeze commit in a clean checkout gives a byte-identical
result (checked on 2026-11-24).

Commits on 2026-11-24 (local times shown by `git log`): hold-out pre-registration `ce11764`, rules frozen `ba13998`,
hold-out first run `b0f6128`. Until they are pushed, their order rests on our own clock; once pushed, GitHub records
when they arrived.

## Limits

* All data are lab recordings of attacks, mostly a handful of events each. Real false-alarm rates need real
  organisations' logs; none were available.
* Several AI datasets are labelled by Splunk as synthetic model-invocation logs.
* "Impenetrable" is not a property any detection or response system can have or prove. What can be shown is what is
  caught, what is missed, and how fast and how proportionately the response follows; that is what this document reports.
